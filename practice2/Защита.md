# Краткая защита практики 2

1. Что сделано? Backend на Go отдаёт HTML/JS/CSS и /api/items; записи хранятся в PostgreSQL. Два контейнера запускаются Docker Compose.
2. Образ и контейнер? Образ — шаблон файловой системы и запуска, контейнер — экземпляр образа с процессом и изменяемым слоем.
3. Зачем два FROM? Компилятор остаётся в builder; в финальный образ копируется только бинарник. Это уменьшает образ и число лишних инструментов.
4. Что кэшируется? Слой скачивания модулей зависит только от go.mod/go.sum. При изменении main.go он не пересоздаётся.
5. Зачем go.sum? Проверяет контрольные суммы модулей; go.mod задаёт зависимости и версии.
6. Почему CGO_ENABLED=0? Позволяет запускать статический Go-бинарник без системной libc в distroless/static.
7. EXPOSE и ports? EXPOSE описывает порт образа. ports публикует порт контейнера на хосте. В работе публикация ограничена 127.0.0.1.
8. Почему DB_HOST=db? В сети Compose имя сервиса разрешается встроенным DNS; localhost внутри app означает сам контейнер app.
9. Почему у базы нет ports? Backend обращается к ней внутри сети, внешний доступ не нужен.
10. Что делает healthcheck? pg_isready проверяет готовность PostgreSQL. depends_on с service_healthy ждёт успешной проверки перед стартом app.
11. Где данные? PostgreSQL использует именованный том db_data. Он сохраняется после compose down. Фронтенд подключён bind mount из каталога хоста, только для чтения.
12. Почему non-root? Процесс не получает привилегии root внутри контейнера; USER 65532:65532. Это дополнительная защита, не полная изоляция.
13. Где пароль? В локальном .env, который исключён из Git и архива. .env.example содержит только инструкцию для замены.
14. Как найти ошибку? compose ps, compose logs app, запрос /healthz, затем проверка БД. В distroless нет bash — вместо входа в shell проверяют логи и API.
15. Как доказать работу? compose up -d --build; curl http://localhost:8080/api/items; показать два объекта, логи, размер и пользователя образа.
