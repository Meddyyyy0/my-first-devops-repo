# Практика 4 Отчёт о локальном выполнении
Шведов Андрей Александрович, БСБО-13-25. 8 ноября 2026.

## Результат
Развёрнут Mattermost 9.5.0 с MySQL 8.0, создан тестовый администратор, команда, приватный канал и пять контрольных сообщений на русском языке. Сделана резервная копия MySQL. Пользовательские данные перенесены в PostgreSQL 15, приложение обновлено до Mattermost 12.0.1.

Проверено через API: вход под прежней учётной записью успешен, ID приватного канала и всех пяти сообщений сохранились, тексты совпадают полностью. Проверка SQL до запуска приложения также подтвердила совпадение всех 8 записей Posts, включая системные сообщения.

## Первый и повторный запуск
Первый успешный запуск создал целевую схему PostgreSQL, выполнил data-only перенос, восстановил индексы, сравнил сообщения, запустил Mattermost 12.0.1 и после HTTP-проверок установил .migration_completed. MySQL-контейнер удалён через --remove-orphans, исходный MySQL volume сохранён.

Повторный запуск завершился успешно с сообщением «Migration already completed: skipping backup and pgloader». После него повторно подтверждено наличие пяти сообщений через API.

Журналы успешных запусков находятся в verification/first-run.log и verification/second-run.log. Пароли из журналов удалены. Дополнительно приложен api-check.txt.

## Обнаруженные и исправленные проблемы
1. В PDF некорректно указан драйвер MySQL и часть синтаксиса workflow; исправлены.
2. Официальный pgloader x86_64 выдавал SBCL memory fault при эмуляции на Apple Silicon. Собран нативный образ из Dockerfile официального репозитория Mattermost.
3. Прямой перенос схемы MySQL создавал несовместимый db_migrations и не создавал PostgreSQL enum channel_type. Использована родная PostgreSQL-схема той же исходной версии Mattermost и официальный генератор data-only конфигурации.
4. В генераторе migration-assist v0.0.2 строка search_path записывалась как единый идентификатор. Скрипт явно нормализует search_path роли на public до и после переноса.
5. Клиент MySQL по умолчанию выводил кириллицу вопросительными знаками. Для дампа и контрольной выборки явно указан utf8mb4.

## Идемпотентность
До успешного завершения источником остаётся сохранённая MySQL. При повторе прерванной миграции пересоздаётся только целевая PostgreSQL-схема. После успеха перенос пропускается. Флаг находится вне Git checkout; блокировка предотвращает параллельные локальные миграции. В workflow также настроен concurrency.

## Что ещё требуется для полной сдачи
Workflow .github/workflows/migration.yml подготовлен, но два запуска в GitHub Actions НЕ выполнялись. Нужны репозиторий с веткой migration, self-hosted runner с доступом к подготовленному Docker-стенду и три GitHub Secrets. Локальные логи нельзя выдавать за логи GitHub Actions.

Сохранение загруженных вложений и аватаров отдельно не проверялось: до переноса их не добавляли. Общий том пользовательских файлов настроен в обоих стеках одинаково. Плагины исходного стенда не использовались; их пользовательские данные не заявлены как мигрированные.

Реализация отличается от буквального include drop в шаблоне: используется пересоздание целевой схемы + официальный data-only перенос. Это нужно объяснить преподавателю. Исходный упрощённый способ был проверен и не запускал обновлённое приложение.

## Защита
Показать compose ps, версию 12.0.1, ответ API, приватный канал с исходными сообщениями и второй запуск с пропуском переноса. Объяснить, почему нельзя переносить служебный журнал миграций MySQL как PostgreSQL, зачем нужен общий том файлов и почему флаг ставится только после проверки приложения.
